# معماری ۳ مقطع × ۳ اپ «همیار من»

## تصمیم معماری
پروژه باید **یک کدبیس مشترک + ۹ Android flavor + محتوای بیرونی نسخه‌گذاری‌شده** داشته باشد.

### نگاشت رسمی
| مقطع | پایه‌ها | flavor | applicationId |
|---|---|---|---|
| ابتدایی | ۴، ۵، ۶ | p04/p05/p06 | com.hamyareman.p04 … p06 |
| متوسطه اول | ۷، ۸، ۹ | p07/p08/p09 | com.hamyareman.p07 … p09 |
| متوسطه دوم | ۱۰، ۱۱، ۱۲ | p10/p11/p12 | com.hamyareman.p10 … p12 |

منبع واحد این نگاشت: `config/education-catalog.json`.

## اصل طلایی
**کد نباید برای تفاوت درس، کتاب یا آزمایشگاه fork شود.**
تفاوت هر اپ باید در «پروفایل محتوا» و manifest باشد.

هر بستهٔ محتوا باید حداقل این شناسه‌ها را داشته باشد:
- `contentProfileId`
- `gradeId`
- `contentVersion`
- `schemaVersion`
- `subjects[]`
- `books[]`
- `laboratories[]`
- checksum برای فایل‌های بزرگ/مهم

## لایه‌ها
1. **App shell:** ناوبری، حساب، تنظیمات، Sync، اعلان، UI.
2. **Feature layer:** آموزش، کتاب، آزمون، آزمایشگاه، سلامت و ابزارها.
3. **Content contract:** مدل‌های مشترک Lesson/Book/Lab/Quiz.
4. **Content pack:** داده و رسانهٔ مخصوص پایه.
5. **Delivery:** ParsPack/CDN + manifest + checksum.
6. **Cloud state:** Appwrite برای پروفایل، پیشرفت و تنظیمات؛ محتوای حجیم در object storage.

## چرا این روش؟
- یک اصلاح UI یا باگ فقط یک‌بار کدنویسی می‌شود.
- ۹ APK از یک موتور ساخته می‌شوند.
- کتاب/آزمایشگاه هر پایه بدون انتشار APK قابل به‌روزرسانی است.
- اشتباه «محتوای پایه ۹ داخل APK پایه ۸» با manifest/validator قابل تشخیص است.
- Appwrite update channel برای هر applicationId جدا می‌ماند.

## الزامات محتوا
هر درس/کتاب/آزمایشگاه باید ID پایدار داشته باشد؛ عنوان فارسی نباید کلید اصلی باشد.

نمونه:
`grade9.math.lesson.01`
`grade9.physics.lab.03`
`grade10.physics.lab.03`

برای مهاجرت محتوا، ID باید ثابت بماند و فقط `contentVersion` افزایش یابد.

## کتاب‌ها و آزمایشگاه‌ها
- PDF و HTML و رسانه‌ها در APK بسته نشوند مگر برای fallback ضروری.
- manifest باید URL، اندازه، checksum و نسخه را ثبت کند.
- اپ ابتدا manifest را می‌گیرد، سپس فقط موارد لازم را دانلود می‌کند.
- محتوای دانلودشده cache می‌شود.
- شکست دانلود نباید UI را از کار بیندازد؛ fallback آخرین نسخهٔ سالم است.

## انتشار
برای هر پایه:
- APK مستقل
- applicationId مستقل
- update row مستقل
- release tag مستقل
- content profile مستقل

انتشار محتوا و انتشار APK باید دو مسیر مستقل باشند.

## CI/CD لازم
قبل از merge:
- اعتبارسنجی ۹ flavor
- اعتبارسنجی applicationId/update row
- اعتبارسنجی catalog
- unit test
- build حداقل flavorهای تغییرکرده

برای release:
- build همان flavor
- امضا
- checksum
- upload محتوا
- smoke test دانلود ناشناس
- سپس اعلام update در Appwrite

## امنیت
کلید signing نباید در مخزن عمومی باقی بماند. چون نسخه‌های فعلی با کلید موجود سازگارند، مهاجرت کلید باید به‌صورت برنامه‌ریزی‌شده انجام شود و بدون شکستن update chain انجام گیرد.

## مدل توسعه پیشنهادی
Feature مشترک → یک PR  
تغییر محتوای پایه → content PR  
انتشار APK پایه → release workflow همان پایه  
انتشار محتوای پایه → content workflow همان profile

این جداسازی جلوی رشد پروژه به ۹ کپی مستقل و ایجاد اختلاف رفتاری بین اپ‌ها را می‌گیرد.
