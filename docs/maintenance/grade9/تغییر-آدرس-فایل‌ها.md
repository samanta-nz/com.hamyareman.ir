# تغییر آدرس یک دسته فایل — چه چیزی لازم است

مرجع کد در زمان نوشتن: `ContentCatalog.kt`، `ServerResolver.kt`،
`RemoteHtmlCache.kt`، `StudyMedia.kt`، `MathHtmlAssets.kt`.

---

## ۰) خلاصهٔ یک‌خطی

نگاشت آدرس‌ها **داخل APK کامپایل شده** و از سرور قابل override نیست؛ پس امروز
هر تغییر آدرس = **یک انتشار جدید APK**. تنها استثنا لینک خودِ فایل نصبی
(`internalUrl`) است که از ردیف Appwrite می‌آید.

---

## ۱) «آدرس» سه لایه دارد

هر فایل در اپ دو شناسه دارد که نباید قاتی شوند:

| لایه | مثال | کجا تعریف شده | تغییرش یعنی |
|---|---|---|---|
| **میزبان داخلی** | `https://c539776.parspack.net` | `ServerResolver.INTERNAL_PUBLIC` (ثابت Kotlin) | تغییر کد + انتشار |
| **کلید/مسیر** روی سرور داخلی | `html ها/یوگا/07 - درخت.html` | `server-map.json` و `catalog.json` (assets) | فقط JSON + انتشار |
| **شناسهٔ فایل** (fileId) | `yga-07` یا `C905f01d01.pdf` | `catalog.json` فیلد `aw`، یا **هاردکد در Kotlin** | تغییر کد + Appwrite + انتشار |

نشانی نهایی این‌طور ساخته می‌شود:

```
داخلی : INTERNAL_PUBLIC + "/" + urlencode(هر بخش کلید)
خارجی : <appwrite>/storage/buckets/<bucket>/files/<fileId>/view?project=<p>
```

یعنی **آدرس سرور خارجی اصلاً از مسیر پیروی نمی‌کند** و فقط تابع fileId است.
پس اگر فقط پوشه‌بندی داخلی را عوض کنید، سمت Appwrite هیچ کاری لازم نیست.

---

## ۲) سناریوی رایج: جابه‌جایی یک دسته (فقط تغییر مسیر)

مثلاً `html ها/یوگا/` → `content/yoga/`. کم‌هزینه‌ترین حالت است چون fileId
دست‌نخورده می‌ماند.

1. **روی پارس‌پک کپی کن، پاک نکن.** کلید تازه را بنویس و کلید قدیمی را نگه
   دار. (`scripts/put_public_object.py` یا یک copy سمت سرور.)
2. **`server-map.json`** — فیلد `key` همان ردیف‌ها را عوض کن.
3. **`catalog.json`** — فیلد `key` همان آیتم‌ها را هم عوض کن.
   ⚠️ **هر دو لازم است.** صفحهٔ دسته‌ها (`ContentScreens`) مستقیم از
   `item.key` کاتالوگ می‌خواند، ولی `ContentCatalog.keyFor()` (که ابزارها و
   صوت/PDF از آن استفاده می‌کنند) از `server-map` می‌خواند و آن را override
   می‌کند. اگر فقط یکی را عوض کنی، نیمی از اپ به آدرس قدیمی می‌رود.
4. `python3 scripts/list_content_urls.py` برای بازتولید فهرست نشانی‌ها.
5. versionCode را بالا ببر و منتشر کن.
6. بعد از اینکه مطمئن شدی همه آپدیت گرفته‌اند، کلیدهای قدیمی را پاک کن.

---

## ۳) چیزهایی که راحت از قلم می‌افتند

### ۳-۱) تغییر **نام فایل** لینک‌های داخل HTML را می‌شکند

```kotlin
relativeFiles = map.values.associate { it.key.substringAfterLast('/') to it.id }
fun itemIdForRelativeFile(fileName: String): String? = relativeFiles[...]
```

HTMLهای آموزشی به هم لینک نسبی دارند (مثل `02-handwriting.html`) و این نگاشت
از **آخرین بخش مسیر** ساخته می‌شود. نتیجه:

* تغییر **پوشه** بی‌خطر است.
* تغییر **نام فایل** یعنی باید محتوای HTMLها را هم ویرایش کنی، وگرنه لینک
  داخلی به بن‌بست می‌خورد.

### ۳-۲) کل cache کاربران باطل می‌شود

```kotlin
private fun file(ctx, fileId, url) = File(dir(ctx), digest("$fileId|$url") + ".hmk1")
```

نام فایل cache از **URL** ساخته می‌شود. با عوض‌شدن آدرس:

* همهٔ کاربران آن دسته را دوباره دانلود می‌کنند (یوگا ≈ ۳۸ مگابایت،
  آموزشگاه ≈ ۲۹ مگابایت).
* فایل‌های قدیمی cache **خودکار پاک نمی‌شوند**؛ `RemoteHtmlCache.clear()` فقط
  دستی صدا زده می‌شود. اگر دسته بزرگی را جابه‌جا کردی، بهتر است در همان نسخه
  یک‌بار `clear()` را اجرا کنی.

### ۳-۳) شناسهٔ PDF و صوت در Kotlin هاردکد است، نه JSON

```kotlin
// MathHtmlAssets.kt
"C905f%02dd%02d.pdf".format(...)
// StudyMedia.kt
out += "C905_E%02d-L%02d_AUDIO.mp3".format(...)
```

به‌علاوه ۳۸ نام فایل در ۱۴ فایل زیر `shared/feature-study/.../books/`.
پس **تغییر نام یک PDF یا صوت، تغییر کد است، نه ویرایش JSON.** اگر انتخابی
هست، مسیر را عوض کن نه شناسه را.

### ۳-۴) `PDF ها` و `grades/grade9/study` قاعدهٔ یکسان ندارند

۲۵ تا از ۲۸ PDF زیر `PDF ها` هستند و ۳ تای فصل ۸ زیر `grades/grade9/study`.
هر اسکریپت دسته‌ای باید روی `server-map.json` کار کند، نه روی حدسِ الگوی مسیر.

### ۳-۵) اسکریپت‌های کمکی قدیمی، آدرس کهنه دارند

`scripts/verify_public_content.py` هنوز `fra.cloud.appwrite.io`، باکت
`6aa1eaae…` و دامنهٔ آروان را هاردکد دارد — یعنی نتیجه‌اش دیگر معتبر نیست.
چند ورک‌فلوی قدیمی (`sync-arvan.yml`، `upload-apk-arvan.yml`،
`release-grade9-v2.yml`، …) هم همچنان به آروان اشاره می‌کنند. اگر از آن‌ها
استفاده می‌کنید، باید هم‌زمان به‌روز شوند.

| کاری که می‌خواهی | JSON | کد Kotlin | فایل روی سرور | انتشار APK |
|---|:--:|:--:|:--:|:--:|
| جابه‌جایی پوشهٔ یک دسته | ✔ (هر دو فایل) | — | کپی | ✔ |
| تغییر نام فایل‌های یک دسته | ✔ | — | کپی | ✔ + ویرایش لینک داخل HTML |
| تغییر میزبان سرور داخلی | — | ✔ یک ثابت | انتقال کامل | ✔ |

| تغییر لینک خود فایل نصبی | — | — | آپلود | ✖ (فقط ردیف Appwrite) |

## ۵) پیشنهاد: این وابستگی به انتشار را یک‌بار برای همیشه بردار

همین حالا ثابت شده که پیکربندی از سمت سرور کار می‌کند: `internalUrl` نسخهٔ
۲٫۲ در payload ردیف `app_release_grade9` می‌آید و به همین دلیل نسخه‌های
نصب‌شدهٔ ۲٫۱ **بدون یک خط تغییر کد** فایل را از پارس‌پک گرفتند.

همان الگو برای نگاشت محتوا هم قابل اجراست:

* یک ردیف `content_map` در `app_state` با یک JSON کوچک
  `{ "base": "...", "overrides": { "<fileId>": "<key جدید>" } }`.
* `ContentCatalog` بعد از خواندن assets، اگر ردیف تازه‌تر بود رویش overlay کند
  (assets به‌عنوان fallback آفلاین باقی بماند).
* از آن به بعد جابه‌جایی هر دسته، و حتی تعویض کل سرور داخلی، **یک ویرایش ردیف
  است، نه انتشار APK**.

هزینه: یک تغییر کوچک در `ContentCatalog` و یک اسکریپت انتشار ردیف. سودش این
است که دیگر هیچ‌وقت برای جابه‌جایی فایل مجبور به آپدیت اجباری نیستی.
